# 11 — Deployment Architecture

**Firefly X TalkTable — Production Deployment, CI/CD, Observability, and Disaster Recovery Specification**

Document owner: CTO · Status: Approved for implementation · Applies to: Phase 2+ target architecture, with Phase 1 (current Vercel + Neon MVP) notes where relevant.

## 1. Environment Strategy

TalkTable runs three first-class environments. Every engineer can reproduce production behavior locally; nothing ships to production without passing through staging.

| Property | Local | Staging | Production |
|---|---|---|---|
| Purpose | Development, unit/integration tests | Pre-release verification, pilot demos, load tests | Live restaurants, real billing |
| Web hosting | `next dev` via `npm run dev` (custom `server.ts` with Socket.io) | Vercel preview/staging project | Vercel production project (`talktable-inky.vercel.app` → custom domain `app.talktable.io`) |
| Database | Phase 1: local Postgres / Neon branch. Phase 2+: Firebase Emulator Suite (Firestore, Auth, Functions, Storage, Pub/Sub) | Neon staging branch → dedicated Firebase project `talktable-staging` | Neon production → Firebase project `talktable-prod` |
| AI provider | Anthropic API with dev key, low rate limits, prompt-logging ON | Anthropic API, staging key, prompt-logging ON | Anthropic API, production key, prompt-logging redacted (PII stripped) |
| Stripe | Stripe test mode + `stripe listen` webhook forwarding | Stripe test mode, dedicated webhook endpoint | Stripe live mode |
| Secrets | `.env.local` (gitignored), template in `.env.example` | Vercel env vars (staging scope) + Google Secret Manager | Vercel env vars (production scope) + Google Secret Manager, rotation every 90 days |
| Data | Seed script (`npm run db:seed`) — demo restaurant, demo users | Anonymized production-shaped synthetic data; never real customer data | Real data; access via break-glass IAM only |
| Auth domains | `localhost:3000` | `staging.talktable.io` | `app.talktable.io`, `*.talktable.io` tenant subdomains (Phase 5 white-label) |

### 1.1 Local development (Firebase emulator era, Phase 2+)

```bash
# One command brings up the full stack
npm run dev:full
# = concurrently:
#   firebase emulators:start --only firestore,auth,functions,storage,pubsub --import ./seed
#   next dev (server.ts wrapper for Socket.io until listener migration completes)
#   stripe listen --forward-to localhost:3000/api/webhooks/stripe
```

Rules:
- Emulator seed data is checked into `./seed` and regenerated by `npm run seed:export` so all engineers share identical fixtures.
- No engineer ever holds production service-account keys on a laptop. Production access is via short-lived tokens (`gcloud auth` with IAM conditions, 1-hour TTL).
- Feature flags (`@vercel/flags` initially, LaunchDarkly at Phase 4) default OFF locally unless overridden in `.env.local`.

### 1.2 Environment promotion flow

```
feature branch ──PR──▶ preview deploy (ephemeral) ──merge──▶ staging (auto) ──manual approval──▶ production (staged rollout)
```

Ephemeral preview environments get an isolated Neon database branch (Phase 1) or a namespaced Firestore prefix in `talktable-staging` (Phase 2+), created and destroyed by CI.

### 2.2 Region strategy for Jordan / MENA

There is no Vercel or Firebase region inside Jordan. The decision criteria are: lowest round-trip latency from Amman, data-residency optionality (see doc 15), and Firestore multi-region availability.

**Measured/expected RTT from Amman (Orange JO / Zain JO fixed + 4G, median of 50 pings):**

| Region | Provider region ID | RTT from Amman (ms) | Firestore available | Notes |
|---|---|---|---|---|
| Frankfurt | Vercel `fra1` / GCP `europe-west3` | 55–75 | Yes | **Primary choice.** Best balance of latency + service availability |
| Tel Aviv | GCP `me-west1` | 15–30 | Yes | Lowest latency but politically unusable for a Jordan-first product; excluded |
| Dammam (KSA) | GCP `me-central2` | 35–55 | Yes | **Phase 5 data-residency option for GCC chains** |
| Doha | GCP `me-central1` | 40–60 | Limited services | Backup MENA option |
| Zurich | GCP `europe-west6` | 60–80 | Yes | DR pair candidate for Frankfurt |
| London | Vercel `lhr1` / `europe-west2` | 75–95 | Yes | Acceptable fallback |
| Bahrain | AWS `me-south-1` | 30–50 | N/A (AWS) | Reference only; we are GCP-committed for backend |
| US East | `iad1` / `us-east1` | 140–180 | Yes | Too slow for realtime order UX; never primary |

**Decisions:**
1. **Vercel functions region: `fra1` (Frankfurt).** Static assets served from Vercel edge PoPs (closest PoP to Amman is typically Frankfurt/Istanbul) — diners get edge-cached menu shells at <50 ms.
2. **Firebase project region: `europe-west3` (Frankfurt)** for Firestore, Functions, Storage — co-located with Vercel compute so SSR→Firestore hops stay <5 ms.
3. **Neon (Phase 1): `eu-central-1`** — already co-located with `fra1`.
4. **Anthropic API** is US-routed; we budget 600–1200 ms first-token for chat and mask it with streaming UI. Voice (Phase 2) uses streaming STT→LLM→TTS pipeline with partial responses (see doc 12).
5. **Phase 5:** GCC enterprise tenants can be pinned to `me-central2` (Dammam) via the tenant-isolation layer (doc 15 §4).

### 2.3 Realtime layer

- **Phase 1 (today):** Socket.io on the custom Node server. On Vercel this degrades; the deployed MVP relies on polling fallback for serverless paths. Acceptable for pilot only.
- **Phase 2 target:** Firestore `onSnapshot` listeners replace Socket.io for order/waiter-request fan-out (kitchen and waiter dashboards subscribe to `restaurants/{id}/orders where status in [...]`). This removes the stateful server entirely and is the architectural unlock for pure-Vercel deployment. ADR-002 in doc 15 records this decision.

## 3. CI/CD Pipelines

All pipelines are GitHub Actions. Branch protection on `main`: PR required, 1 approval, all checks green, linear history.

### 3.3 Production deploy with staged rollout — `.github/workflows/deploy-prod.yml`

```yaml
name: Production Deploy
on:
  push:
    branches: [main]

concurrency: { group: prod-deploy, cancel-in-progress: false }

jobs:
  staging:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - uses: actions/checkout@v4
      - name: Deploy to staging
        run: |
          npm i -g vercel@latest
          vercel pull --yes --environment=production --token=${{ secrets.VERCEL_TOKEN_STAGING }}
          vercel deploy --prod --token=${{ secrets.VERCEL_TOKEN_STAGING }}
      - name: Migrate staging DB
        env: { DATABASE_URL: ${{ secrets.STAGING_DATABASE_URL }} }
        run: npx prisma migrate deploy
      - name: Staging smoke tests (synthetic order lifecycle)
        run: BASE_URL=https://staging.talktable.io npx playwright test --grep @synthetic

  production:
    needs: staging
    runs-on: ubuntu-latest
    environment: production   # requires manual approval in GitHub environment settings
    steps:
      - uses: actions/checkout@v4
      - name: Migrate production DB (expand-only migrations enforced)
        env: { DATABASE_URL: ${{ secrets.PROD_DATABASE_URL }} }
        run: |
          # Guard: refuse destructive SQL in migrations touching prod
          ! grep -rEi 'DROP TABLE|DROP COLUMN' prisma/migrations/$(ls prisma/migrations | tail -1) \
            || { echo "Destructive migration blocked — use expand/contract"; exit 1; }
          npx prisma migrate deploy
      - name: Deploy to Vercel (no traffic yet — skew protection on)
        id: deploy
        run: |
          npm i -g vercel@latest
          vercel pull --yes --environment=production --token=${{ secrets.VERCEL_TOKEN }}
          url=$(vercel deploy --prebuilt --prod --skip-domain --token=${{ secrets.VERCEL_TOKEN }} || vercel deploy --prod --skip-domain --token=${{ secrets.VERCEL_TOKEN }})
          echo "url=$url" >> "$GITHUB_OUTPUT"
      - name: Canary 10% for 15 minutes
        run: |
          vercel promote ${{ steps.deploy.outputs.url }} --token=${{ secrets.VERCEL_TOKEN }} # with Rolling Releases configured at 10%→50%→100%
      - name: Watch error rate during canary
        run: |
          for i in $(seq 1 15); do
            sleep 60
            rate=$(curl -s -H "Authorization: Bearer ${{ secrets.SENTRY_TOKEN }}" \
              "https://sentry.io/api/0/organizations/talktable/sessions/?field=sum(session)&statsPeriod=10m&groupBy=session.status" \
              | jq '[.groups[] | select(.by["session.status"]=="errored") | .totals["sum(session)"]] | add // 0')
            echo "errored sessions (10m): $rate"
            if [ "$rate" -gt 25 ]; then echo "Canary failing — aborting"; exit 1; fi
          done
      - name: Promote to 100%
        run: vercel rolling-release approve --token=${{ secrets.VERCEL_TOKEN }}
      - name: Tag release
        run: |
          git tag "release-$(date +%Y%m%d-%H%M)" && git push --tags
      - name: Notify
        run: |
          curl -X POST ${{ secrets.SLACK_DEPLOY_WEBHOOK }} -H 'Content-type: application/json' \
            --data "{\"text\":\"TalkTable prod deploy ${{ github.sha }} fully rolled out\"}"
```

Firebase Functions (Phase 2+) deploy from a parallel job using `firebase deploy --only functions --project talktable-prod` with `--force` disabled and Functions traffic split (`gcloud functions deploy --set-traffic`) mirroring the same 10/50/100 stages.

### 3.4 Rollback procedure — `.github/workflows/rollback.yml`

```yaml
name: Rollback Production
on:
  workflow_dispatch:
    inputs:
      reason:
        description: 'Why (links to incident)'
        required: true
      target_deployment:
        description: 'Vercel deployment URL/ID to restore (blank = previous)'
        required: false

jobs:
  rollback:
    runs-on: ubuntu-latest
    environment: production
    steps:
      - name: Instant alias rollback (web)
        run: |
          npm i -g vercel@latest
          if [ -n "${{ inputs.target_deployment }}" ]; then
            vercel rollback ${{ inputs.target_deployment }} --token=${{ secrets.VERCEL_TOKEN }} --yes
          else
            vercel rollback --token=${{ secrets.VERCEL_TOKEN }} --yes
          fi
      - name: Freeze deploys
        run: gh variable set DEPLOY_FROZEN --body "true" -R ${{ github.repository }}
        env: { GH_TOKEN: ${{ secrets.GITHUB_TOKEN }} }
      - name: Open incident issue
        run: |
          gh issue create -R ${{ github.repository }} \
            --title "INCIDENT: production rollback $(date -u +%FT%TZ)" \
            --body "Reason: ${{ inputs.reason }}. Deploys frozen until postmortem." \
            --label incident
        env: { GH_TOKEN: ${{ secrets.GITHUB_TOKEN }} }
      - name: Page on-call
        run: |
          curl -X POST https://events.pagerduty.com/v2/enqueue -H 'Content-Type: application/json' -d \
            '{"routing_key":"${{ secrets.PD_ROUTING_KEY }}","event_action":"trigger","payload":{"summary":"Prod rollback executed: ${{ inputs.reason }}","severity":"critical","source":"github-actions"}}'
```

**Rollback rules (runbook):**
1. **Code rollback** is alias-flip on Vercel: < 60 seconds, zero build. Always safe because DB migrations are **expand-only** (new columns nullable, old code never broken by new schema; contraction happens ≥1 release later).
2. **Schema rollback** is never automated. If a contract migration must be reverted, on-call restores from Neon point-in-time (Phase 1) or Firestore PITR (Phase 2+) into a side database and runs the documented data-repair script with a second engineer reviewing.
3. **Feature-flag rollback first.** If the regression is behind a flag, kill the flag (propagates < 30 s) before touching deploys.
4. **Functions rollback (Phase 2+):** `gcloud functions deploy --set-traffic <prev-revision>=100`.

## 4. Monitoring & Observability

### 4.1 Stack

| Concern | Tool | Notes |
|---|---|---|
| Error tracking (web + functions) | **Sentry** | `@sentry/nextjs`; release tagging from CI; source maps uploaded on deploy; PII scrubbing (phone numbers, table tokens) via `beforeSend` |
| Uptime / synthetic | **BetterStack (Uptime)** | 30 s checks from Frankfurt + Bahrain probes; synthetic order journey every 5 min hitting a dedicated `synthetic-restaurant` tenant |
| Web vitals / RUM | Vercel Speed Insights + Sentry Performance | Per-surface budgets (§6) |
| Logs | Vercel log drains → BetterStack Logs (Phase 1) → Cloud Logging (Phase 2+) | Structured JSON; `requestId`, `restaurantId`, `tableId` on every line |
| Firestore usage | GCP Monitoring dashboard | Reads/writes/deletes per collection, per tenant label; document count growth |
| AI cost | Custom `ai_usage` ledger (per-request token counts written by `/api/ai/chat`) + daily Cloud Function rollup → dashboard | Cost per restaurant, per order, per conversation; drives unit economics in doc 13 |
| Billing integrity | Daily reconciliation job: completed orders count vs ledger entries vs Stripe invoice line items | Any drift > 0 pages on-call (billing correctness is existential) |

### 4.2 Dashboards (Grafana / GCP Monitoring)

1. **Service Golden Signals** — request rate, p50/p95/p99 latency per route group (`/api/orders`, `/api/ai/chat`, `/r/*`), error rate, saturation (function concurrency, Neon connections / Firestore op quotas).
2. **Restaurant Operations Health** — orders/hour per restaurant, time-to-accept (order placed → kitchen accepted), waiter-request response time, realtime listener disconnect rate. This dashboard is also the basis of the customer-facing status view.
3. **AI Quality & Cost** — conversations/hour, tokens in/out, cost/conversation, containment rate (conversations resolved without waiter escalation), fallback-to-human rate, Anthropic API error/latency.
4. **Billing & Revenue** — completed orders (billable events) per restaurant, daily accrued JOD, invoice status, Stripe webhook failures, reconciliation drift (must be 0).
5. **Firestore/DB usage** — ops/sec vs capacity plan (doc 15 §9), hot-document warnings (>1 write/sec sustained on a single doc), index usage, storage growth.

### 4.3 Alerting thresholds

| Alert | Condition | Severity | Action |
|---|---|---|---|
| API availability | 5xx rate > 2% over 5 min on order/auth routes | P1 page | On-call immediately |
| Order pipeline stall | 0 orders accepted platform-wide for 10 min during restaurant operating hours despite orders placed | P1 page | Likely realtime layer failure |
| AI chat down | `/api/ai/chat` error rate > 20% over 5 min | P2 page | Feature-degrade: UI auto-switches to menu-only ordering (graceful degradation flag) |
| AI cost anomaly | Hourly AI spend > 3× trailing 7-day same-hour average | P2 page | Possible prompt loop/abuse; per-table rate limiter check |
| Latency budget | p95 TTFB > 800 ms on `/r/*` for 15 min | P3 ticket | Investigate within business day |
| Billing drift | Reconciliation delta ≠ 0 | P1 page | Freeze invoicing job, manual audit |
| DB saturation | Neon connections > 80% of pool / Firestore ops > 70% of planned capacity for 10 min | P2 page | Scale plan in runbook |
| Cert/domain | TLS expiry < 14 days, domain check fail | P3 ticket | Automated renewal verification |
| Stripe webhooks | > 3 consecutive webhook delivery failures | P2 page | Replay from Stripe dashboard |
| Synthetic journey | QR→order→accept synthetic fails 2× consecutively | P1 page | Full-path outage suspected |

### 4.4 On-call & escalation

- **Rotation:** weekly, 2 engineers (primary/secondary), PagerDuty. Until team ≥ 6, founders are permanently secondary.
- **Escalation ladder:** P1 → primary (ack within 5 min) → secondary (after 10 min) → CTO (after 20 min). P2 → primary, ack within 30 min. P3 → next business day ticket.
- **Restaurant-hours weighting:** Jordan dinner peak is 18:00–23:00 Asia/Amman; alert sensitivity is doubled (halved thresholds) in this window via scheduled alert policies.
- **Postmortems:** blameless, within 48 h of any P1, template in repo (`docs/runbooks/postmortem-template.md`), action items tracked as GitHub issues with `incident-followup` label and 2-week SLA.

## 5. Backup & Disaster Recovery

### 5.1 Targets

| Data class | RPO | RTO | Mechanism |
|---|---|---|---|
| Orders, billing ledger | ≤ 5 min | ≤ 1 h | Neon PITR (Phase 1) / Firestore PITR 7-day (Phase 2+) |
| Menus, knowledge base, CRM | ≤ 1 h | ≤ 4 h | Same + daily export |
| Media (menu images) | ≤ 24 h | ≤ 8 h | GCS dual-region bucket, versioning on |
| Config/secrets | 0 (versioned) | ≤ 1 h | IaC repo + Secret Manager versions |
| Full-platform regional loss | ≤ 24 h | ≤ 24 h | Cross-region export restore drill (below) |

### 5.2 Backup schedule

- **Phase 1 (Neon):** PITR enabled (continuous WAL, 7-day window) + nightly `pg_dump` to GCS `gs://talktable-backups-eu` (lifecycle: 30 daily, 12 monthly, 7-year retention for billing tables per Jordan tax requirements).
- **Phase 2+ (Firestore):** PITR enabled (7-day). Scheduled managed export **every 6 hours** via Cloud Scheduler → `firestore.googleapis.com/v1/...:exportDocuments` to `gs://talktable-firestore-exports` (dual-region `eur4`). Collection-scoped daily exports of `billing_ledger` and `orders` additionally copied to a second project (`talktable-dr`) with separate IAM — protects against project-level compromise.
- **Stripe** is its own system of record for invoices; we mirror invoice metadata nightly into the ledger DB for reconciliation, never the reverse.

### 5.3 DR runbook & drills

1. **Quarterly restore drill:** restore latest Firestore export into `talktable-dr`, run automated row-count + checksum verification against production snapshot, record time-to-usable. Drill report attached to compliance evidence (doc 15 §8).
2. **Region-loss scenario (Frankfurt down):** Vercel auto-fails static/edge to other PoPs; backend restore = import latest export into pre-created `europe-west6` (Zurich) Firestore database, flip `FIREBASE_PROJECT` env, redeploy. Documented step-by-step; target ≤ 24 h, measured in drills.
3. **Billing ledger is append-only** (ADR-006, doc 15): corruption recovery = replay from order events, which makes even worst-case ledger restore deterministic.

## 6. Performance Budgets & Load Testing

### 6.1 Budgets per surface (p75 on mid-range Android over 4G, Amman)

| Surface | TTFB | LCP | INP | Notes |
|---|---|---|---|---|
| `/r/[slug]/[tableToken]` (diner menu) | ≤ 400 ms | ≤ 2.0 s | ≤ 200 ms | The money page. Menu shell ISR-cached at edge; images AVIF + `next/image`, ≤ 120 KB above fold |
| AI chat first streamed token | — | — | — | ≤ 1.8 s after send; typing indicator at 300 ms |
| Order submit → confirmation UI | — | — | — | ≤ 1.0 s optimistic, ≤ 3.0 s server-confirmed |
| Kitchen dashboard (tablet, Wi-Fi) | ≤ 300 ms | ≤ 1.5 s | ≤ 150 ms | New order appears on screen ≤ 2 s after diner submits (end-to-end realtime budget) |
| Waiter dashboard | ≤ 300 ms | ≤ 1.5 s | ≤ 150 ms | Waiter call ≤ 2 s propagation |
| Manager analytics | ≤ 600 ms | ≤ 2.5 s | ≤ 200 ms | Heavy charts allowed to lazy-load |
| Platform admin (Phase 4) | ≤ 800 ms | ≤ 3.0 s | ≤ 200 ms | Internal tolerance |

Budgets enforced in CI: Lighthouse CI (`lhci autorun`) against the preview deploy with assertion file; regression > 10% fails the PR.

### 6.2 Load test plan (k6, run against staging before each phase launch)

**Traffic model:** a busy restaurant ≈ 40 tables, dinner peak = 0.5 orders/table/hour, 3 AI messages/order, dashboards holding persistent listeners. Test at 1×, 10× (Phase 3: 50 restaurants), 100× (Phase 5: 500 restaurants) scale.

| Scenario | Profile | Pass criteria |
|---|---|---|
| S1 Menu browse storm | 2,000 VUs ramp over 5 min hitting `/r/*`, 20 min soak | p95 TTFB < 600 ms, 0 5xx |
| S2 Order lifecycle | 200 orders/min sustained: create → kitchen accept → ready → complete (drives billing events) | p95 order create < 800 ms; realtime fan-out < 2 s; ledger count == orders count |
| S3 AI chat concurrency | 300 concurrent conversations, streaming | first token p95 < 2.5 s under load; graceful 429 + retry on Anthropic limits, no dropped conversations |
| S4 Realtime fan-out | 500 dashboards listening, 50 orders/min broadcast | listener update p95 < 2 s, reconnect storm recovery < 30 s |
| S5 Billing month-end | Generate invoices for 500 tenants × 30k ledger rows | job completes < 30 min, idempotent on re-run |
| S6 Chaos | Kill Anthropic (mock 500s), kill realtime, slow DB +300 ms | Diner can still place menu-only orders; clear degraded-mode UX; alerts fire as specified §4.3 |

Load test results, with flame graphs and capacity headroom conclusions, are attached to each phase's exit-criteria review (doc 12).

## 7. Infrastructure as Code & Change Management
